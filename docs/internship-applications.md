# DOC-F16 Internship Applications

## Purpose

The Internship Applications workspace tracks an opportunity from interest to a private outcome. It does **not** contact employers, submit applications, scrape email, or publish outcomes.

## Ownership boundary

All application, contact, note, reminder, requirement and outcome records are keyed to the authenticated prototype principal (`X-Luma-Student-Id`). Production authentication should replace this development identity header without changing the service ownership rules.

## Status workflow

The supported transition graph is centralized in `apps/api/app/modules/internships/service.py`:

- Interested → Preparing | Withdrawn
- Preparing → Interested | Applied | Withdrawn
- Applied → Awaiting Response | Interviewing | Offer | Rejected | Withdrawn
- Awaiting Response → Interviewing | Offer | Rejected | Withdrawn
- Interviewing → Awaiting Response | Offer | Rejected | Withdrawn
- Offer / Rejected / Withdrawn are closed outcomes.

Every transition is appended to `application_events`. Closed applications may be archived with optional private outcome notes.

## Recommended opportunity imports

DOC-F28 is not implemented in this release. DOC-F16 therefore accepts a recommendation **snapshot** from the existing LumaPath recommendation UI. `source_reference` is unique per student, so repeatedly importing the same recommendation returns the existing application rather than duplicating it.

No external opportunity provider is contacted by DOC-F16.

## Requirements and readiness

Application requirements are student-entered or copied from an existing LumaPath recommendation. The backend checks those names against owner-scoped Portfolio evidence generated by DOC-F14.

- `demonstrated` means matching recorded Portfolio evidence exists.
- `not_demonstrated` means the current evidence snapshot does not demonstrate the requirement.

The latter is **not** a claim that the student lacks the skill. The API returns at most three focused readiness actions linking back to Portfolio or Skills.

## Dates, reminders and quiet hours

Deadlines, interview dates and follow-up dates have separate confirmation flags. LumaPath does not treat an unconfirmed date as authoritative.

Deadline/interview/follow-up reminders require the corresponding date to be confirmed first. Reminder records include:

- IANA timezone
- enabled state
- notification preference
- quiet-hour start/end
- requested reminder time
- effective notification time after quiet-hour adjustment

A disabled notification preference keeps the private reminder but sets `effective_notification_at = null`.

DOC-F16 stores reminder intent; it does not send email or employer communication.

## Planner integration

Planner task creation uses a two-step boundary:

1. Student enters and explicitly confirms a task time.
2. FastAPI validates it against the confirmed application deadline/interview/follow-up date.
3. Only then does the frontend add the returned action to the existing Planner through `addTask`.

The server response is idempotent by application + idempotency key. Custom preparation tasks still require explicit timing confirmation but are not tied to an application date.

## Idempotency

Creation, status changes, reminder creation and planner approvals use idempotency keys. Repeated recommendation imports are additionally de-duplicated by `source_reference` per owner.

## Privacy

Contacts, notes and outcome notes are never placed in analytics, Portfolio evidence or public views by DOC-F16. The feature has no employer outreach endpoint.
